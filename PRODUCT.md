# Product

## Platform

web

## Users

Developers who run `review-loop` from Claude Code, and the teammates and reviewers they share results with. The developer uses the dashboard to set up and start loops and to go back over how a change was reviewed. Teammates read it as a record of that review: what the reviewer raised, how the coder answered, and the verdict.

## Product Purpose

`agents-pp` runs pair-programming workflows for coding agents. Its first workflow, **review-loop**, pairs Claude (the coder) with an independent CLI reviewer (Codex, Claude, ...). The loop repeats until the reviewer approves, the round cap is reached, or the user cancels. Every round is written to disk.

The dashboard is the UI over that on-disk record. In order of importance, it is for:

1. **Configuring:** backends, models, effort, role prompts and dashboard options, without editing JSON by hand.
2. **Starting loops** from the browser instead of the CLI.
3. **Auditing conversations:** reading the coder/reviewer exchange round by round.

Usage and timing stats (tokens, coder vs reviewer time) are on the page as supporting information, not a primary job.

It succeeds when a user can configure and start a loop, and a teammate can follow how a change was reviewed, without opening the raw files.

## Positioning

The reviewer is a separate agent with its own CLI and model, not the coder checking its own work, and the whole conversation is kept as files that can be audited. Comments have stable IDs (`R<round>-C<n>`). The coder must answer each one as resolved or declined, with a reason. The dashboard shows that accountable, ID-linked exchange. It is not a chat transcript.

## Operating Context

- Generated by `scripts/dashboard.sh` from `templates/dashboard.html`. Loop data is substituted into `{{DATA}}` and the page renders it client-side.
- Opened as a static file (`file://`) or served by `dashboard.sh --serve`, an embedded python3 server on loopback. When served, its only write paths are config set/unset (`/api/config`, auto-saving edits), loop start (`/api/start`) and model catalog refresh (`/api/models`), all behind a per-run token.
- Hash-routed views: `#/` (stats and loop list), `#/loop/<id>`, `#/start`, `#/config`.
- Used next to a terminal running Claude Code. The page can also be shared as evidence of a review.

## Capabilities and Constraints

- **One self-contained file:** no external resources, CDNs or web fonts. It must work from `file://` as well as when served.
- **No build step, no framework:** vanilla JS and CSS in `templates/dashboard.html`, tested with Node (`tests/test_dashboard_*.js`) and the bash suite (`tests/test_loop.sh`).
- **Light and dark themes** that follow `prefers-color-scheme`.
- On a static page, actions that need the server (starting a loop, auto-saving config) fall back to showing the command to run, or to saving through a file the user picks.
- Fixed terminology: coder, reviewer, round, loop, backend, verdict (`approved` / `changes_requested`), blocking, resolved / unresolved / declined-accepted / declined-rejected, round cap, extension (continue).

## Product Principles

1. **The files are the truth.** The UI shows what is on disk and never diverges from it.
2. **Every comment can be traced.** Comment IDs, resolutions and verdicts stay visible and linked across rounds.
3. **The CLI and the page are equal paths.** Anything the page can do is also a command the user can see and run.
4. **Local and safe by default.** No network dependencies; the only writes are narrow, validated ones.

## Accessibility & Inclusion

WCAG 2.2 AA is required: full keyboard operation, visible focus, and sufficient contrast in both light and dark themes.
